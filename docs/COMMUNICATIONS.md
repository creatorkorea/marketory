# 운영 안내 메일

2026-10-12 구현. 검증 결과와 남은 범위는 하단에서 별도로 기록한다. 실제 고객 발송이나 운영 배포를 완료했다는 의미가 아니다.

## 운영 흐름

운영자 또는 플랫폼 관리자는 마켓의 신청자를 선택해 안내 초안을 만든다. 선정·대기·탈락·참가확정·부스·보완 요청·일반 안내의 문구를 제공하며, 제목과 본문을 직접 수정할 수 있다. 이번 범위는 결정적 템플릿이며 AI 생성이 아니다. 수신자는 신청에 저장된 알림 이메일로 고정하고 임의 주소 입력을 허용하지 않는다.

초안 승인은 READY 상태로만 바꾼다. 실제 발송은 별도의 명시적 요청으로 QUEUED에 넣으며 worker가 처리한다. QUEUED는 접수 상태이고 SENT는 메일 제공사가 요청을 수락한 상태다. 수신함 도착·열람 여부는 확인하지 않는다.

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| DRAFT | 검토·편집 중 | 내용 확인 후 승인 |
| READY | 현재 내용 승인됨 | 별도 발송 요청 |
| QUEUED | 발송 대기 | worker 실행 및 상태 확인 |
| SENDING | worker가 처리 중 | 완료 또는 결과 불명 확인 |
| SENT | 제공사 수락 | 추가 안내는 새 초안으로 |
| FAILED | 실패 확인 또는 발송 전 검증 차단 | 원인 확인 후 동일 내용 재시도 또는 새 초안 |
| UNKNOWN | 수락 여부를 확정할 수 없음 | 근거 확인 전 재시도 금지 |

## 변경과 재시도

승인·대기 중 신청 내용·상태, 정책 또는 부스 배치가 바뀌면 기존 승인을 그대로 사용하지 않는다. 발송 시도 전에는 초안으로 되돌리고 재승인한다. 시도 이력이 있으면 내용과 수신자를 보존하며 변경된 정보로 새 초안을 만든다. 발송 중이거나 결과가 불명확한 메일은 먼저 결과를 확인해야 한다.

동일 내용 재시도에는 같은 제공사 요청 키를 사용한다. 발신 주소도 첫 시도에서 고정한다. Resend의 중복 방지 키 보존은 24시간이므로, 구현은 첫 시도 후 23시간을 넘으면 재시도를 차단하고 새 승인 절차를 요구한다. [Resend 중복 방지 계약](https://resend.com/docs/dashboard/emails/idempotency-keys).

UNKNOWN은 운영자가 제공사 기록 등 실제 근거를 확인하고 시도 ID·근거 참조·사유를 기록한다. 수락 확인은 SENT, 미수락 확인은 FAILED로 바꾸며 불충분한 근거는 UNKNOWN을 유지한다. 클라이언트가 제공사 조회를 수행했다고 주장하는 값만으로 상태를 바꾸지 않는다.

## 발송 설정

서버의 gitignored `apps/api/.env`에 `MARKETORY_RESEND_API_KEY`를 보관한다. 로그인 OTP용 Supabase SMTP 키와 별도다. 브라우저의 NEXT_PUBLIC 변수나 저장소에 키를 넣지 않는다.

`MARKETORY_EMAIL_DELIVERY_ENABLED`는 기본 false다. 키가 존재하는 것만으로 발송하지 않는다. 실제 발송에는 worker의 활성 설정·제공사 키·프로세스 실행이 필요하다. API 설정은 화면의 발송 활성 상태 표시에 사용하므로 실제 운영 방식과 일치시킨다. 활성화 이후 worker의 단회 실행도 대기 메일을 처리할 수 있으므로 단순 DB 상태 확인용으로 사용하지 않는다.

기본 발신 주소는 `마켓토리 <marketory@send.creatorkorea.org>`다. 테스트에서는 주입한 제공사와 가짜 HTTP 응답을 사용한다. 실제 인증·도메인 발송 권한·지정 수신함 도착 검증은 별도 증거가 필요하다.

## 권한과 기록

검수자·조회자·셀러에게 운영 메일 원문과 변경 API를 제공하지 않는다. 승인·발송 요청 시 현재 권한을 재검사하고 worker도 요청자의 현재 운영 권한을 확인한다. 모든 변경은 요청 키와 버전을 검사하며 감사 기록과 요청 결과를 함께 저장한다. 발송 시도·결과 확인 이력을 남기고, 처리 중인 요청 결과를 만료시켜 중복 처리를 허용하지 않는다.

## 실제 운영 화면 → worker 검증 — 2026-10-12

실제 관리자 OTP 로그인 후 Chrome 운영 화면에서 비공개 `[TEST] 운영 메일 E2E 20261012` 마켓을 생성했다. 안내 생성 → 테스트 제목·본문 저장 → 내용 2판 승인 → 별도 발송 요청을 실제 API로 처리했다. DB의 승인자·승인 판·대기 상태를 확인한 뒤 기존 `process_one` worker를 한 번 실행했다. 실제 Resend 접수 후 DB와 운영 화면의 `SENT`(제공사 접수 완료), 시도 1회, 제공사 식별자 `01a12ec6-b716-7024-bbdc-169d9c863e3f`를 확인했다. 남은 QUEUED/SENDING은 0건이며 감사 기록에는 생성·수정·승인·발송 요청·worker 처리가 남았다.

검증 범위는 안내 생성부터 제공사 접수까지다. 선행 셀러 프로필과 신청은 명시적인 합성 테스트 데이터를 DB에 준비했다. 실제 셀러 신청·동의 절차를 검증한 것이 아니다. 동의 데이터에는 `test_fixture=true`, `consent_accepted=false`를 기록했고 설정 감사 기록도 남겼다. 테스트 마켓은 DRAFT로 유지하며, `[TEST]` 셀러 프로필과 신청·메일 이력은 검증 증거로 남아 있다. 셀러 프로필은 실사용 전에 실제 정보로 작성해야 한다.

대기열에 지정 메시지 한 건만 있는지 확인하고, 제공사 호출 직전에도 메시지 ID·수신자·제목·본문 해시가 일치하는지 검사했다. 발송 활성화는 해당 단회 프로세스 설정에만 적용했다. `.env`와 상시 발송 설정은 false를 유지했다. 실행 시작 기록이 있으면 재실행을 거부하도록 해 테스트 중복 발송을 방지했다.

이번 메일 제목은 `[마켓토리 TEST] 운영 화면 승인·워커 발송 검증 20261012`다. 이전 연결 테스트 메일의 사용자 수신 확인과 별개이며, 이번 메일의 받은편지함 도착은 아직 확인하지 않았다. 로컬 실행 검증이므로 배포 환경의 상시 worker 검증은 남아 있다. 이 검증에서 발견한 목록 상태 갱신 누락은 아래 후속 보완으로 수정했다.

### 목록 상태 갱신 보완 — 2026-10-12

상세 조회에 성공하면 현재 페이지의 동일 메시지 목록 항목도 최신 응답으로 갱신한다. 더 오래된 버전으로 목록을 덮지 않으며 페이지 건수·순서·다른 항목은 보존한다. `최신 상태 확인`은 제목·본문 입력을 바꾸지 않고 비교 결과를 표시한다. 운영자가 비교를 확인하면 상세 기준 버전과 처리 상태가 갱신된다. 자동 폴링은 추가하지 않았다.

회귀 테스트에서 외부 발송 상태 변경 후 목록 갱신 실패를 먼저 재현했다. 수정 후 메일 브라우저 테스트 10개와 Next.js 프로덕션 빌드가 통과했다. 테스트는 가짜 인증/API를 사용하며 이번 UI 보완 과정에서는 메일을 추가 발송하지 않았다.

## 무료 MVP 운영안 — 2026-10-14

권장안은 **운영 담당자가 정해진 시간에 로컬 PC에서 승인된 큐를 단회 처리**하는 방식이다. 현재는 운영안 준비 단계이며 발송 활성화·예약 실행·실제 수신자 발송은 하지 않았다. PC가 꺼져 있거나 담당자가 실행하지 않으면 큐가 대기하므로 즉시 자동 발송을 약속하지 않는다. 행사와 담당자가 정해진 뒤 확인 주기·연락 지연 허용 범위를 결정한다.

Render Free는 Background Worker와 one-off job을 지원하지 않으며 무료 웹 서비스는 유휴 시 중지될 수 있다. 현재 API 안에서 별도 무한 루프를 돌리거나 상태 확인 호출로 기동을 유지하는 방식은 채택하지 않는다. [Render 무료 서비스 제약](https://render.com/docs/free). 상시 처리가 필요해지면 별도 worker 예산 또는 다른 실행 환경을 비교하고 승인 후 연결한다. 이번 작업에서 유료 자원이나 다른 서비스에 비밀값을 추가하지 않았다.

### 실행 전에 반드시 구분할 사항

- 화면의 승인(READY), 발송 요청(QUEUED), 제공사 수락(SENT)은 각각 별개다. SENT를 받은편지함 도착으로 설명하지 않는다.
- `python -m marketory.worker --once`는 dry-run이 아니다. 발송이 켜져 있으면 오래된 SENDING을 UNKNOWN으로 정리하고, 전체 DB 대기열에서 최대 한 건을 처리한다. ID를 생략하면 전체 큐를 처리한다. 아래 지정 실행 옵션을 사용하면 해당 메일만 처리하며 오래된 SENDING 복구는 실행하지 않는다. 한 건 처리가 검증 차단으로 끝날 수도 있다.
- 프로세스 종료 코드 0은 발송 성공을 보장하지 않는다. 발송 비활성, 빈 큐, 키 미설정, FAILED/UNKNOWN 처리도 종료 코드만으로 구분할 수 없다. 실행 후 해당 메시지 상태와 시도 기록을 반드시 조회한다.
- 코드상 실제 발송 활성화는 worker 프로세스 설정에 필요하다. API 설정은 화면의 발송 활성 상태 표시에 사용하므로 운영 방식과 일치시켜야 한다. 로컬 단회 시험에서는 `.env`나 배포 설정을 영구 변경하지 않는다.

### 담당자용 단회 처리 절차

1. 사용할 코드 revision·대상 DB·발신 도메인·Resend 한도·담당자·실행 시간을 확인한다. 키는 서버 설정에서만 읽고 출력하거나 메모에 복사하지 않는다.
2. 운영 화면에서 마켓·신청자·수신자·제목·본문·현재 신청/부스 상태를 확인하고 승인한다. 실제 발송할 메시지를 별도 요청해 QUEUED로 만든다. 외부 발송은 명시적으로 승인된 대상에만 수행한다.
3. 시스템 담당자가 **전체 DB**의 QUEUED/SENDING/UNKNOWN을 읽기 전용으로 확인한다. 승인된 메시지 ID를 지정하고 다른 worker 실행 여부를 확인한다. ID 없는 일반 `--once`는 다른 대기 건도 선택할 수 있으므로 수동 발송에는 사용하지 않는다. 지정 실행은 다른 대기 메일을 선택하지 않지만 다른 worker의 실행 자체를 중단하지는 않는다.
4. 승인된 대상의 ID를 지정해 담당자가 단회 worker를 실행한다. 환경변수 활성화는 해당 프로세스에만 적용하고 종료 후 이전 값을 복원한다. 실행이 중단되거나 결과를 확인할 수 없으면 재실행하지 말고 먼저 DB·제공사 기록을 확인한다.
5. 운영 화면에서 최신 상태를 조회해 메시지 ID·시도 횟수·최종 상태·제공사 식별자를 기록한다. 첫 실운영 전 지정 테스트 수신함 도착을 별도 확인한다. 이미 검증한 2026-10-12 수신 증거가 새 메일 수신을 증명하지 않는다.
6. FAILED는 사유를 해결한 뒤 화면의 승인/재시도 규칙을 따른다. UNKNOWN은 제공사 기록을 근거로 확인 처리하며 동일 메시지를 새로 만들어 우회 발송하지 않는다. 장시간 대기나 행사 종료로 검증이 차단되면 현재 문맥으로 새 초안을 검토한다.

발송 없는 DB 상태 확인은 저장소 루트에서 다음과 같이 실행할 수 있다. 이 명령은 현재 프로세스의 활성 설정을 잠시 false로 덮어쓰고 복원한다. 큐 복구나 제공사 호출을 수행하지 않는다.

```powershell
$previousDelivery = $env:MARKETORY_EMAIL_DELIVERY_ENABLED
$previousPythonPath = $env:PYTHONPATH
try {
    $env:MARKETORY_EMAIL_DELIVERY_ENABLED = 'false'
    $env:PYTHONPATH = (Resolve-Path 'apps/api/src').Path
    & apps/api/.venv/Scripts/python.exe -m marketory.worker --once
    if ($LASTEXITCODE -ne 0) { throw 'DB 상태 확인 실패' }
} finally {
    $env:MARKETORY_EMAIL_DELIVERY_ENABLED = $previousDelivery
    $env:PYTHONPATH = $previousPythonPath
}
```

### 실운영 전 남은 조건

운영 담당자와 확인 주기, 실제 발송 대상, 테스트·실운영 데이터 구분, PC 접근 통제, Resend 실제 계정 한도, 결과 불명 확인 담당자가 필요하다. 지정 실행은 아래 옵션으로 제공한다. 승인된 내용·수신자 확인은 계속 필요하며, 명령은 내용 해시나 기대 버전을 입력받지 않는다. 자동 예약 실행·일괄 발송·상시 worker는 이번 범위에 포함하지 않는다.

검증: 2026-10-14 로컬 격리 PostgreSQL에서 worker/provider 테스트 **29개 통과(37.63초)**. 발송 비활성·키 미설정 시 claim 차단, 동시 claim 중복 방지, 재시도 키/발신자 보존, 권한·문맥 재검사, 오래된 claim 및 timeout의 UNKNOWN 처리를 포함한다. 제공사는 테스트 대역이며 실제 메일을 보내지 않았다. 증거는 Git 제외 `output/mail-operations-20261014.xml`이다.

### 지정 메일 단회 실행 — 2026-10-14 후속 구현

`--once --communication-id <UUID>`를 추가했다. 이미 승인·접수된 QUEUED 메시지 중 지정 ID만 선택하고, 대상이 없거나 다른 상태/잠금 상태이면 다른 메일로 넘어가지 않는다. 기존 claim 잠금·요청자 권한·행사 종료·신청/정책/부스 문맥·승인 판 검사·제공사 중복 방지 키를 그대로 사용한다. 동일 ID 동시 실행도 기존 잠금과 상태 재검사로 보호한다.

지정 모드는 전역 `recover_stale`을 호출하지 않는다. 대상이 SENDING/UNKNOWN이면 미처리로 끝나므로 별도 근거 확인 절차를 따른다. 옵션 없이 실행하는 기존 worker의 복구·전체 큐 처리는 유지한다. UUID 형식 오류나 `--once` 없는 ID 옵션은 설정 로딩 전에 거절한다.

발송 승인 후에만 실행할 명령 형태는 아래와 같다. `PYTHONPATH=apps/api/src` 또는 API 패키지 설치가 필요하다. ID는 운영 화면에서 확인한 실제 승인 대상 값으로 대체한다. 이 명령 자체는 활성 설정을 켜지 않는다.

```text
apps/api/.venv/Scripts/python.exe -m marketory.worker --once --communication-id <승인된-메시지-UUID>
```

지정 모드 종료 코드: 0=대상을 처리함(검증 차단 FAILED나 제공사 UNKNOWN 포함, 발송 성공 보장 아님), 1=DB 확인/실행 오류, 2=처리하지 않음(비활성·키 미설정·대상 없음·비대기·잠금 등). CLI 인자 오류도 2다. 출력은 처리 여부만 표시하며 이메일·본문·키는 출력하지 않는다. 실제 결과는 메시지 상태·시도 기록으로 확인한다. 기능 검증 중 실제 메일 발송과 배포 설정 변경은 수행하지 않았다.

후속 통합 검증: 관련 API·worker·provider·CLI·foundation 53개 통과, 실제 연결 환경의 발송 비활성 차단 및 큐/시도/감사 불변 확인. 상세 범위는 [QA 기록](qa/README.md)의 2026-10-14 지정 메일 실행 점검을 따른다. 실제 활성 발송·수신 검증과 상시 worker 배포를 완료 처리하지 않는다.
