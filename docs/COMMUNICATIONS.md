# 운영 안내 메일

2026-10-12 구현. 검증 결과와 남은 범위는 하단에서 별도로 기록한다. 실제 고객 발송이나 운영 배포를 완료했다는 의미가 아니다.

## 운영 흐름

운영자 또는 플랫폼 관리자는 마켓의 신청자를 선택해 안내 초안을 만든다. 선정·대기·탈락·참가확정·부스·보완 요청·일반 안내의 문구를 제공하며, 제목과 본문을 직접 수정할 수 있다. 이번 범위는 결정적 템플릿이며 AI 생성이 아니다. 수신자는 신청에 저장된 알림 이메일로 고정하고 임의 주소 입력을 허용하지 않는다.

초안 승인은 READY 상태로만 바꾼다. 실제 발송은 별도의 명시적 요청으로 QUEUED에 넣으며 worker가 처리한다. QUEUED는 접수 상태이고 SENT는 메일 제공사가 요청을 수락한 상태다. 수신함 도착·열람 여부는 확인하지 않는다.

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| DRAFT | 검토·편집 중 | 내용 확인 후 승인 |
| READY | 현재 내용 승인됨 | 별도 발송 요청 |
| QUEUED | 발송 대기 | worker 실행 및 상태 확인 |
| SENDING | worker가 처리 중 | 완료 또는 결과 불명 확인 |
| SENT | 제공사 수락 | 추가 안내는 새 초안으로 |
| FAILED | 실패 확인 또는 발송 전 검증 차단 | 원인 확인 후 동일 내용 재시도 또는 새 초안 |
| UNKNOWN | 수락 여부를 확정할 수 없음 | 근거 확인 전 재시도 금지 |

## 변경과 재시도

승인·대기 중 신청 내용·상태, 정책 또는 부스 배치가 바뀌면 기존 승인을 그대로 사용하지 않는다. 발송 시도 전에는 초안으로 되돌리고 재승인한다. 시도 이력이 있으면 내용과 수신자를 보존하며 변경된 정보로 새 초안을 만든다. 발송 중이거나 결과가 불명확한 메일은 먼저 결과를 확인해야 한다.

동일 내용 재시도에는 같은 제공사 요청 키를 사용한다. 발신 주소도 첫 시도에서 고정한다. Resend의 중복 방지 키 보존은 24시간이므로, 구현은 첫 시도 후 23시간을 넘으면 재시도를 차단하고 새 승인 절차를 요구한다. [Resend 중복 방지 계약](https://resend.com/docs/dashboard/emails/idempotency-keys).

UNKNOWN은 운영자가 제공사 기록 등 실제 근거를 확인하고 시도 ID·근거 참조·사유를 기록한다. 수락 확인은 SENT, 미수락 확인은 FAILED로 바꾸며 불충분한 근거는 UNKNOWN을 유지한다. 클라이언트가 제공사 조회를 수행했다고 주장하는 값만으로 상태를 바꾸지 않는다.

## 발송 설정

서버의 gitignored `apps/api/.env`에 `MARKETORY_RESEND_API_KEY`를 보관한다. 로그인 OTP용 Supabase SMTP 키와 별도다. 브라우저의 NEXT_PUBLIC 변수나 저장소에 키를 넣지 않는다.

`MARKETORY_EMAIL_DELIVERY_ENABLED`는 기본 false다. 키가 존재하는 것만으로 발송하지 않는다. 발송 활성화에는 API·worker 설정과 worker 프로세스 실행이 필요하다. 활성화 이후 worker의 단회 실행도 대기 메일을 처리할 수 있으므로 단순 DB 상태 확인용으로 사용하지 않는다.

기본 발신 주소는 `마켓토리 <marketory@send.creatorkorea.org>`다. 테스트에서는 주입한 제공사와 가짜 HTTP 응답을 사용한다. 실제 인증·도메인 발송 권한·지정 수신함 도착 검증은 별도 증거가 필요하다.

## 권한과 기록

검수자·조회자·셀러에게 운영 메일 원문과 변경 API를 제공하지 않는다. 승인·발송 요청 시 현재 권한을 재검사하고 worker도 요청자의 현재 운영 권한을 확인한다. 모든 변경은 요청 키와 버전을 검사하며 감사 기록과 요청 결과를 함께 저장한다. 발송 시도·결과 확인 이력을 남기고, 처리 중인 요청 결과를 만료시켜 중복 처리를 허용하지 않는다.

## 검증 결과

2026-10-12: 전체 API 테스트 110개 통과(450.35초). 새 메일 API 10개, worker/provider/foundation 37개와 문맥 재검사 추가 검증을 포함한다. 모든 제공사 호출은 테스트 대체 구현 또는 MockTransport이며 실제 메일을 보내지 않았다. Ruff와 OpenAPI 생성 타입 일치 검사 통과.

실제 Supabase 프로젝트 `xtuznofafxlwlggnolns`에 `20261011134640_communications.sql` 한 건을 CLI dry-run 후 적용했다. migration 이력, 신규 테이블 3개 RLS 활성, anon/authenticated/PUBLIC 직접 접근 grant 0개를 확인했다. 적용 후 security advisors의 warn 이상 결과는 0개다. 기존 고객 데이터 생성·변경이나 발송 활성화는 수행하지 않았다.

웹 단위 63개·브라우저 fixture 50개(신규 메일 화면 8개)와 프로덕션 빌드가 통과했다. 데스크톱·모바일 캡처에서 입력 폼·동작 버튼·가로 넘침을 확인했다. 브라우저는 인증/API를 대체한 fixture이며 실제 Resend 인증·지정 수신함 도착·운영 배포 검증은 남아 있다. 마지막 UNKNOWN 선택 초기화 보완 후 재빌드와 메일 브라우저 9개를 다시 통과했다. 증빙은 gitignored `output/communications-browser.json`(전체 50개), `output/communications-browser-final.json`(최종 메일 9개), `output/communications-desktop.png`, `output/communications-mobile.png`다.

화면 경로는 `/markets/{project_id}/communications`이며 목록 안에서 상세를 연다. 요청 복구 범위를 유지하기 위해 별도 메시지 상세 URL은 만들지 않았다. 개별 메시지 링크 공유는 후속이다.
