## 처리와 복구 경계

웹은 업무 변경을 API에 요청합니다. API는 사용자와 권한을 검사하고 업무 변경·감사·비동기 작업 등록을 하나의 DB 트랜잭션으로 기록합니다. worker는 DB에 기록된 작업을 claim하여 처리하며, 기존 명세의 claim_token·revision·재시도·UNKNOWN 규칙을 유지합니다.

작업 상태를 프로세스 메모리에만 두지 않습니다. 재배포·종료 후에도 DB 기록으로 복구하고, 오래된 worker 결과가 최신 작업을 덮어쓰지 않도록 검증합니다. 이미지 공유는 프로세스 메모리 공유를 뜻하지 않습니다. API와 worker는 독립적으로 실행됩니다.

별도 Redis나 추가 큐 서비스는 이번 결정에 포함하지 않습니다. DB 작업 저장·claim의 구체적인 구현과 연결 방식은 P0/P3에서 결정합니다. 실제 외부 발송의 UNKNOWN을 단순 재시도로 해결하지 않습니다.

### 모집을 여는 순서

1. 실제 행사와 TEST 마켓을 구분한다. 테스트 식별자 목록을 유지하고 실운영 명단·발송 대상에서 제외한다. 프로젝트 이름 구분만으로 데이터 환경 격리가 완료되지는 않는다.
2. 관리자 화면에서 새 마켓 초안을 만들고 모든 시각을 KST로 대조한다. 정책 문구·버전·정원·비용을 행사 책임자가 확인한다.
3. 이메일 인증을 마친 담당자에게 필요한 마켓 역할만 배정한다. 다른 마켓 접근 차단과 해제 후 접근 차단을 확인하고 권한 변경 사유를 남긴다. 관리자 계정을 공유하지 않는다.
4. 외부 발송이 꺼진 상태와 테스트/운영 데이터 범위를 확인하고 백업 시점을 기록한다.
5. 모집 공개 확인창에서 대상 이름·상태·사유를 확인한다. 별도 비로그인 화면에서 조건과 신청 가능 여부를 대조한다.
6. 실제 기기의 승인된 테스트 계정으로 신청·첨부·심사·확정·배치·안내를 리허설한다. 실제 법적 동의는 임의로 대신 수락하지 않는다.
7. 종료할 때에는 마켓 설정에서 ‘심사 중’으로 전환하고 공개 페이지의 신청 불가와 API accepting_applications=false를 확인한다. 종료는 기존 신청 삭제를 뜻하지 않는다.

### 매일 운영 점검

- 모집 시작 전 웹 로그인 페이지, API `/health/ready`, 관리자 목록과 셀러 본인 신청을 확인한다. 웹 `/api/health`의 생존 응답만으로 DB 정상까지 단정하지 않는다.
- 미처리 신청·보완 기한·참가확정 기한·미배정 팀을 확인한다. 선정과 참가확정, 배치 초안과 확정 배치를 구분한다.
- 메일은 큐 등록·제공사 접수·실제 수신을 구분한다. 현재 worker가 없으므로 큐 등록을 발송 완료로 안내하지 않는다.
- 퇴사·담당 변경 시 마켓 배정을 회수하고 감사 기록을 확인한다. 요청 결과 재조회와 첨부 조회도 회수된 권한으로 차단되는지 점검한다.
- 백업 성공 시각, 담당자, 산출물 위치, 복원 가능한 마지막 시점을 기록한다. 실패 시 담당자에게 알리고 복구 가능 시점을 다시 평가한다.

### 백업·복원 계획

DB, private Storage 파일, 배포 설정 목록과 코드 revision을 한 묶음으로 관리한다. DB 백업에는 Storage 객체 본문이 포함되지 않으므로 파일은 별도로 보존해야 한다. Supabase 무료 프로젝트는 정기 export와 외부 보관을 계획하고, 현재 계정에서 실제 제공되는 백업 기능·보관기간을 확인한다. [Supabase 공식 백업 안내](https://supabase.com/docs/guides/platform/backups).

1. 백업 책임자가 접근 통제된 보관 위치·주기·보관기간과 비용을 먼저 확정한다. 비밀값·DB dump·첨부 원본을 Git이나 일반 공유 링크에 넣지 않는다.
2. 쓰기 일시 중지 시간 또는 일관된 스냅샷 기준을 정한다. DB export와 파일 목록/본문의 대상 시각을 맞추고 파일 수·크기·체크섬 및 스키마 버전을 기록한다.
3. Auth 데이터와 사용자 ID 연계, DB 역할, 버킷 정책, SMTP/redirect/CORS, 배포 환경변수 이름도 복원 범위에 포함한다. 설정 목록에는 비밀값을 넣지 않고 안전한 별도 보관 위치만 참조한다.
4. 운영과 분리된 복구 대상에 복원한다. 메일 발송과 worker는 비활성화하고 운영 도메인·운영 수신처를 연결하지 않는다. 운영 DB에 시험 복원을 덮어쓰지 않는다.
5. 마켓·신청·첨부 건수, 상태·버전, 부스 중복 여부, 감사 이력, private 파일 열람과 권한 차단을 대조한다. 인증 로그인은 별도로 검증한다.
6. DB 복원 시 이미 발송된 메일이 과거 QUEUED/SENDING 상태로 돌아올 수 있다. 제공사 이력과 작업 기록을 대조하기 전에는 worker를 시작하지 않는다. UNKNOWN을 근거 없이 재발송하지 않는다.
7. 복구 소요시간·누락 범위·재개 승인자를 기록한 뒤에만 연결을 전환한다. 실패하면 원래 환경을 유지하고 원인을 수정한다.

현재 상태: 절차 작성 완료. 아래 합성 로컬 DB 복원 리허설은 통과했다. 실제 운영 백업 파일 생성·Storage 백업·운영 환경 복원은 미실행이며, 승인된 보관 위치와 복구 대상이 정해진 뒤 실행한다.

## 합성 로컬 DB 백업·복원 리허설 — 2026-10-13

사용자가 실제 행사는 미정이며 테스트 기준 진행을 선택했다. `scripts/rehearse_local_restore.py`를 추가해 재현 가능한 리허설을 실행했다. 운영 DSN 입력은 받지 않으며 `127.0.0.1:55432`의 로컬 개발 DB에서 이번 실행이 만든 고유한 테스트 DB만 사용한다. 실제 Supabase 프로젝트에는 접속하지 않는다.

실행 순서: 기존 migration을 적용한 소스 DB 생성 → 합성 셀러 신청·참가확정·부스 확정 → PostgreSQL 17 `pg_dump` custom archive → 새 DB에 `pg_restore --single-transaction --exit-on-error` → 대조 및 실제 API 검증 → 생성 DB 정리. 외부 인증은 기존 테스트 대역을 사용하고 worker는 실행하지 않는다.

결과: **PASS**. public/auth 16개 테이블의 29개 합성 행을 정렬된 JSON 해시로 대조해 모두 일치했다. 복원 후 authenticated 역할의 직접 신청 테이블 접근 거절, 셀러 본인 신청·A01 부스 조회, 타 계정 신청 조회 거절, 취소 후 활성 부스 배정 회수를 확인했다. 복원 DB를 변경한 뒤 소스 데이터가 그대로인 것도 대조했다. 복원 명령은 0.578초, 합성 데이터 준비·검증을 포함한 실행 구간은 약 6.2초이었다. 이 수치는 작은 로컬 fixture 측정이며 운영 복구 목표 시간의 보장이 아니다.

재현(저장소 루트, 로컬 PostgreSQL 실행 및 API 개발 의존성 설치 후):

```powershell
node scripts/local-db.mjs
# DB를 유지한 상태에서 별도 터미널
apps/api/.venv/Scripts/python.exe scripts/rehearse_local_restore.py --pg-bin 'C:/Program Files/PostgreSQL/17/bin'
```

도구 경로만 지정 가능하며 원격 DB URL/기존 DB 이름을 인자로 받지 않는다. 합성 dump와 결과는 Git 제외 `output/marketory_restore_<고유값>/`에 저장한다. 이번 증거: `output/marketory_restore_7c7d532122224419845e9ff2e7586429/result.json`, 같은 폴더의 `synthetic.dump`. 실제 개인정보 백업용 도구가 아니며 비밀값 또는 운영 dump를 이 출력 경로에 복사하지 않는다.

한계: 같은 로컬 PostgreSQL 클러스터의 기존 역할을 사용하므로 새 호스트의 전역 역할·비밀번호 복구를 증명하지 않는다. auth.users는 테스트용 최소 테이블이며 Supabase Auth 전체 구조·세션·OTP 복원 증거가 아니다. Storage 객체·서명 링크·SMTP·환경변수·도메인 전환·실제 장애 중 쓰기 일관성은 포함하지 않는다. 이 항목은 보관 위치·복구 대상·운영 담당자가 확정된 후 별도 실증한다. 현재 상시 메일 발송과 실제 행사 모집은 계속 보류한다.

## 무료 메일 운영 절차 준비 — 2026-10-14

[운영 안내 메일](COMMUNICATIONS.md)에 담당자 로컬 단회 실행 권장안, 전체 대기열 사전 확인, 종료 코드와 발송 결과 구분, UNKNOWN 대응, 발송 없는 DB 확인 명령을 추가했다. 실제 계정 한도·담당자·확인 주기는 미정이며 예약/상시 실행은 활성화하지 않았다. 현재 CLI는 특정 메시지 지정 기능이 없어 다중 마켓의 임의 한 건 발송 수단으로 사용하지 않는다.

worker/provider 로컬 테스트 29개 통과. 발송 비활성 환경을 명시한 `marketory.worker --once`는 실제 연결 DB에서 `worker_probe database=available`로 종료했다. 이 실행은 제공사 호출·대기열 복구를 하지 않는다. 제품 코드와 배포 환경 설정은 변경하지 않았으며 실제 메일도 발송하지 않았다.

### 후속: 지정 메일 단회 실행 구현

같은 날 후속 요청으로 `--once --communication-id <UUID>`를 구현했다. 지정한 QUEUED 메시지만 기존 검증·claim 경로로 처리하고 대상이 없거나 비대기 상태이면 다른 대기 메일로 넘어가지 않는다. 이 모드는 전체 오래된 SENDING 복구를 생략한다. 위 절의 '지정 기능 없음'은 문서 정리 당시 상태이며 후속 구현으로 해소됐다. 명령·종료 코드·남은 운영 조건은 [운영 안내](COMMUNICATIONS.md)의 지정 실행 절을 따른다.

새 테스트 5개의 실패를 먼저 확인한 후 구현했다. worker/provider/foundation/CLI 42개 테스트 통과(42.69초), 추가한 지정/일반 실행 동시 claim 검사 2개 통과(8.32초), Ruff 검사·포맷 검사 통과. 중복되는 기존 동시 claim 1개를 제외하면 43개 시나리오다. 두 마켓의 대기 메일 중 지정 대상만 처리하고 이미 처리된 ID·없는 ID로 재실행해도 다른 큐와 시도 기록이 그대로임을 로컬 DB로 검증했다. 외부 제공사는 테스트 대역이며 실제 발송·배포 설정 변경은 하지 않았다. 회귀 결과는 Git 제외 `output/targeted-mail-20261014.xml`에 기록했다(추가 동시 실행 시나리오는 터미널 결과).
