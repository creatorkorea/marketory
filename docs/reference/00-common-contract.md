## 플리마켓 플랫폼 MVP 변경요약과 공통계약

Version 1.3  |  2026.10.08

개발자가 다섯 명세서를 같은 기준으로 구현하도록 인증, 상태, 데이터, 발송과 완료조건을 통일한다. 인증·신청·발송·요청 복구에 적용할 현재 규칙을 본문에 통합했으며 이전 변경 내역은 부록으로 분리했다. 이 문서는 개발 기준안이며 실제 서비스 구현이나 운영 검증 결과를 의미하지 않는다.

| DRAFT / SUBMITTED / NEED_INFO / REVIEWING / APPROVED / WAITING / CONFIRMED | cancel | CANCELLED | SELLER / OPERATOR | 사유 필수·event_end_at 이전·배치 해제와 발송 무효화 |
| NEED_INFO | extend_info | NEED_INFO | OPERATOR | RECRUITING/REVIEWING, 만료 여부와 무관하게 새 기한·사유·version 검사 |

표에 없는 상태 전환은 409로 차단한다. PLATFORM_ADMIN은 감사 사유를 남기고 OPERATOR 액션을 실행할 수 있다. AI는 최종 상태를 변경할 수 없다. 프로젝트 COMPLETED에서는 신규 업무 변경을 차단한다. 열람·허용된 출력과 기존 작업의 결과 확인·감사·보관 관리만 허용한다. 신청의 운영완료 Enum은 추가하지 않는다.

필수항목 검증은 제출 전에 수행한다. 실패 시 422와 필드 오류를 반환하고 DRAFT를 유지한다. NEED_INFO는 접수 후 서버 검사 또는 운영자의 증빙 보완요청에 사용한다. SUBMITTED는 접수 완료, REVIEWING은 심사 가능 상태다. 접수 후 보완은 일반 모집기간과 별도로 info_due_at까지 허용한다.

## 4 프로젝트 상태와 역할

<a id="table-04"></a>
**표 04**

| 전환 | 조건과 권한 |
| --- | --- |
| DRAFT→RECRUITING | OPERATOR 공개 액션, 필수설정과 동의 문구 입력 완료 |
| RECRUITING→REVIEWING | 운영자 모집 마감. 모집기간 만료 시 상태 변경 여부와 무관하게 신규 제출 차단 |
| REVIEWING→RECRUITING | 운영자가 사유·새 모집기간 기록 후 재공개 |
| REVIEWING→CLOSED | 운영자 모집·선정 업무 종료 선언, 확정·취소·배치·안내는 event_end_at 이전까지 허용 |
| CLOSED→COMPLETED | event_end_at 경과 후 운영자 최종 종료, 신규 업무 변경 차단, 기존 작업 결과 확인·감사·보관 관리 허용 |
| CLOSED→REVIEWING | event_end_at 이전, OPERATOR가 사유·expected_version을 제출하여 재검토 시작 |

이미 접수한 신청의 심사와 보완은 RECRUITING/REVIEWING이면서 event_end_at 이전에 진행한다. CLOSED에서는 새로운 승인·대기자 승격·재신청을 하지 않는다. 추가 선발이 필요하면 운영자가 사유와 함께 CLOSED→REVIEWING으로 되돌린다. COMPLETED는 MVP에서 재개하지 않는다.

## 7 운영 예외의 공통 결정

공개 가입은 인증 완료 후 서버가 users를 생성하며 global_role=USER, account_role=SELLER, status=ACTIVE를 기본값으로 설정한다. 이름은 셀러 프로필 단계에서 입력하며 그 전에는 null을 허용한다. 로그인만으로 STAFF나 PLATFORM_ADMIN 권한을 부여하지 않는다. 운영자 초대는 별도 관리자 액션이다.

로그인에 사용하는 인증 제공자의 검증 완료 이메일을 안내 주소의 유일한 원본으로 사용한다. 최초 제출 때 applications.notification_email과 notification_email_verified_at으로 복사한다. 계정 이메일 변경은 기존 신청 수신처를 자동 변경하지 않는다. 셀러가 내 신청에서 현재 검증된 계정 이메일로 동기화를 요청한 경우에만 변경하며 임의 주소 입력은 받지 않는다.

업무 변경은 현재시각 < projects.event_end_at이고 프로젝트가 COMPLETED가 아닐 때만 허용한다. 행사 당일에도 이 조건 안에서 참가확정·취소·부스 변경·긴급 안내를 처리한다. 마감 후에는 신규 업무를 만들지 않되 기존 AI/발송 작업 결과 기록, UNKNOWN 결과 확인, 감사로그 추가, 개인정보 보관·삭제 관리 작업은 권한을 검사해 허용한다.

<a id="table-08"></a>
**표 08**

| 예외 | 처리 기준 |
| --- | --- |
| 보완기한 만료 | NEED_INFO 유지, 자동 취소/탈락 없음. 셀러 수정·보완제출을 막고 운영자에게 연장 요청 경로를 안내한다. 운영자는 기한 연장 또는 취소를 선택한다. |
| 발송 결과 불명 | UNKNOWN은 조회/증빙 기반 결과 확인만 허용한다. 접수 확인 시 SENT, 미접수 확정 시 FAILED, 확인 불가 시 UNKNOWN을 유지한다. |
| 발송 내용 수정 | 실행 시도 이력이 없는 DRAFT/READY/QUEUED는 같은 레코드 수정 가능. QUEUED 수정은 worker와 같은 행 잠금 아래 대기 취소·승인 초기화·내용 변경·DRAFT 전환을 하나의 트랜잭션으로 처리한다. worker가 먼저 SENDING을 획득하면 409로 거절한다. 실행 이력이 생긴 메시지의 수신처·내용은 불변, 수정 발송은 새 작업·새 키·새 승인을 요구한다. |
| 부스 교환 | 같은 프로젝트의 관련 신청·부스·배치를 잠그고 전체 목표 배치를 검증한 뒤 해제와 재배정을 한 번에 커밋한다. 중간 실패는 전체 롤백한다. |
| 첨부 변경 | DRAFT 또는 보완기간 내 NEED_INFO의 요청된 첨부만 변경 가능. 업로드 요청과 완료 모두 상태·소유권·version을 다시 검사한다. |

미확인 업무값인 실제 행사 종료시각·발송 제공사·개인정보 보관기간은 운영 책임자가 공개 전에 확정한다. 본 문서의 검증 시나리오는 실행 결과가 아닌 개발 완료조건이다.

REVIEWER의 첨부 조회는 배정 신청의 상품사진에 한정한다. 사업자 증빙은 OPERATOR/PLATFORM_ADMIN만 조회하고 셀러는 본인 파일만 조회한다. REVIEWER/VIEWER 모두 운영자료 내보내기를 허용하지 않는다.

## 8 발송과 요청 복구 계약

<a id="table-09"></a>
**표 09**

| 현재 상태 | 액션 | 다음 상태 | 조건 |
| --- | --- | --- | --- |
| DRAFT | approve | READY | OPERATOR가 현재 내용·수신처 승인, 외부 호출 없음 |
| READY | send | QUEUED | OPERATOR의 명시 발송 요청, 승인버전·대상·행사 종료시각 검사 |
| QUEUED | worker claim | SENDING | 유효한 발송 요청과 현재 권한·대상 검사, 실행 토큰 발급 |
| SENDING | 제공사 응답 | SENT / FAILED / UNKNOWN | 접수 성공 / 미접수 확정 실패 / 결과 불명 구분 |
| FAILED | retry | QUEUED | OPERATOR, 동일 내용·수신처·승인 유효, 미대체 작업만, 제공사 키 유지 |
| UNKNOWN | resolve | SENT / FAILED / UNKNOWN | 제공사 조회 또는 근거 확인, 재호출 없이 결과 확정 |

READY에는 발송 요청이 없으므로 worker는 처리하지 않는다. QUEUED 전에 content_version과 승인·수신처를 고정한다. 발송 요청 기록 queued_at/queued_by와 audit 로그는 QUEUED 변경과 같은 트랜잭션에 저장한다. API의 202는 발송 요청 접수이며 제공사 접수 성공인 SENT와 구분한다.

결과 본문 만료 후에도 사용한 요청 키는 EXPIRED 기록으로 유지한다. 같은 키의 재요청·조회는 410 REQUEST_RESULT_EXPIRED이며 업무를 재실행하지 않는다. 상세 필드와 정리 조건은 DB 명세의 요청 보관 계약을 따른다.

요청 중복 방지 레코드와 업무 변경·이력·비동기 작업 생성은 같은 DB 트랜잭션으로 커밋한다. IN_PROGRESS는 미커밋 처리 중에만 존재하며 별도로 저장하지 않는다. 커밋 전 중단은 전체 롤백, 커밋 후 응답 유실은 같은 키와 본문으로 저장된 결과를 재조회한다. 외부 AI·메시지 호출은 커밋된 작업을 worker가 처리한다.

한 신청에서는 upload-url 발급 → 파일 전송 → complete 성공을 파일 한 개씩 순차 실행한다. complete가 반환한 application_version과 revision_no를 다음 파일 요청에 사용한다. 임시저장·첨부 해제도 같은 클라이언트 변경 대기열에 넣어 동시에 보내지 않는다. 미완료 또는 실패 파일을 해결하기 전에는 제출을 비활성화한다.

발송 대상이 변경되면 READY/QUEUED를 검사한다. 실행 시도 없는 작업은 승인·대기열 정보를 지우고 DRAFT로 되돌린다. 이전 실행 이력이 있는 재시도 작업은 내용 불변을 지키며 FAILED/CONTEXT_CHANGED로 중단하고 수정 발송을 요구한다. 이미 SENDING인 작업은 UNKNOWN/SENT 등 실제 결과를 추적하며 철회 성공으로 표시하지 않는다.
