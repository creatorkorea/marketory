<a id="table-02"></a>
**표 02**

### 2 1 기본 라우팅 규칙

<a id="table-07"></a>
**표 07**

| 조건 | 라우팅 | 운영 의미 |
| --- | --- | --- |
| 필수정보 누락 | 제출 전 DRAFT 유지 / 접수 후 NEED_INFO | 입력 오류와 접수 후 보완을 구분 |
| 동일일자 타 프로젝트 중복 | 경고 생성 → 운영자 확인 | 자동 탈락 없이 일정 충돌만 표시 |

| 탈락 | REJECTED → 종료 | 사유와 안내 이력 보존 |
| 참가취소 | CONFIRMED/APPROVED → CANCELLED | 부스 회수·대기자 승격 검토 |

## 3  단계별 상세 프로세스

### 3 1 프로젝트 생성 모집 준비

<a id="table-08"></a>
**표 08**

| 구분 | 상세 설계 |
| --- | --- |
| 입력 | 프로젝트명, 행사일, 장소, 모집기간, 모집팀 수, 허용/제한 품목, 참가비, 사업자 여부, 사진 필수 여부, 부스·전기·테이블 조건, 심사기준 |
| 처리 | 운영자가 프로젝트를 생성하고 모집정책·운영조건·심사기준을 저장한다. 프로젝트별 상태와 모집기간은 독립 관리한다. |
| 검증 | 모집 시작일≤종료일, 모집팀 수&gt;0, 행사일/필수 심사기준 입력 확인 |
| 출력 | Project 레코드, project_id, 모집상태 |
| 예외 | 모집 시작 후 핵심정책 변경 시 변경이력 기록과 기존 신청자 재안내 |

### 3 2 셀러 신청 프로필 연결

<a id="table-09"></a>
**표 09**

| 3 | 상품·사진·가격대·운영요구 입력 | Application 임시저장 | DRAFT |
| 4 | 동의 후 제출 | 필수항목 검증, 제출시각 기록 | SUBMITTED |
| 5 | 필요시 보완 | 보완항목 수정 | SUBMITTED 재진입 |

## 4  AI 검토 운영자 선정 프로세스

<a id="table-11"></a>
**표 11**

| AI 적용 원칙<br>AI 결과는 “추천”과 “주의사항”이며 자동 탈락 사유가 아니다. Evaluation 결과를 운영자에게 보여주고 최종 승인/대기/탈락은 운영자가 수행한다. |
| --- |

<a id="table-12"></a>
**표 12**

| Agent | 입력 | 주요 처리 | 결과 | Human 확인 |
| --- | --- | --- | --- | --- |
| Application Agent | 신청정보 | 요약, 누락/특이사항 추출 | 요약, 누락 플래그 | 보완요청 여부 |
| Classification Agent | 상품명·설명·사진설명 | 카테고리 자동 분류 | category, 근거 | 운영자 수정 |
| Evaluation Agent | 심사기준 + 신청정보 | 적합성·차별성·운영안정성 평가 | AI 점수·추천이유·위험사항 | 최종 선정 |
| Duplicate Agent | 동일 프로젝트 신청목록 | 유사 업종/상품·과다비중 탐지 | 유사 셀러·중복 경고 | 다양성 판단 |

## 8 보완된 운영 절차

<a id="table-27"></a>
**표 27**

| 상황 | 처리 및 기록 |
| --- | --- |
| 모집 공개 | 운영자가 정책·행사일·모집기간·동의 문구를 등록한 후 RECRUITING으로 전환한다. 공개 조회와 신규 접수 가능 여부는 구분한다. |
| 제출과 검증 | 필수정보가 없으면 422와 필드 오류를 반환하고 DRAFT를 유지한다. 제출 성공 시 SUBMITTED와 제출 snapshot을 저장하고 서버 사전검증을 진행한다. |
| 보완 요청 | 접수 후 SUBMITTED/REVIEWING에서 NEED_INFO로 변경한다. info_requests_json과 info_due_at을 저장하고 보완 안내 초안을 만든다. 일반 모집이 끝나도 요청 기한까지 보완 제출을 허용한다. |
| 검토와 결정 | AI 실패 시 수동심사가 가능하다. 최신 신청 revision과 정책버전이 다른 평가에는 이전 평가 표시를 한다. 운영자는 사유와 함께 승인·대기·탈락을 결정한다. |
| 참가확정 | 승인 시 confirm_due_at을 입력한다. 안내 링크는 로그인 후 소유권을 확인하는 내 신청으로 이동한다. 기한 만료 시 자동 취소하지 않고 운영자가 연장·취소한다. |
| 취소와 승격 | event_end_at 이전이고 프로젝트가 COMPLETED가 아니면 공통 상태표에 따라 취소한다. 상태·배치 해제·READY/QUEUED 안내 무효화·이력을 한 트랜잭션에서 반영한다. 대기자는 후보만 제시하며 자동 승격하지 않는다. |
| 부스 이동 | 기존 활성 배치의 released_at을 기록하고 새 배치를 생성한다. 같은 프로젝트, CONFIRMED, 조건 충족, 중복 없음 검사를 통과해야 확정한다. 이전 배치 레코드는 삭제하지 않는다. |
| 발송 | 초안 수정 → 승인 → READY → 발송 요청 → QUEUED → SENDING → SENT/FAILED/UNKNOWN 순서다. SENT는 제공사 접수 성공이며 실제 도착·열람과 구분한다. UNKNOWN은 확인 전 재발송하지 않는다. |
| 행사 종료 | event_end_at 경과 후 운영자가 projects.status를 COMPLETED로 전환하면 신규 업무 수정은 종료한다. 기존 작업 결과 확인·감사·보관 관리 작업은 허용한다. Application은 CONFIRMED 등을 유지한다. 사후 실적·노쇼 관리 고도화는 후속 범위다. |

모집 중 정책을 바꾸면 policy_version을 증가시키고 변경 전후·사유·영향 대상자를 기록한다. 기존 신청 snapshot은 유지하며 새 기준 적용이 필요한 신청에는 보완요청 또는 재평가를 명시적으로 실행한다. 변경 안내는 초안으로 준비하고 운영자 승인 후 발송한다.

<a id="table-28"></a>
**표 28**

| 상황 | 담당과 순서 | 기록 |
| --- | --- | --- |
| 신규 가입 | 인증 완료 → 서버 기본 SELLER 생성 → 프로필 입력 → 신청 작성 | 인증 user_id, 프로필 완료시각, 권한 부여 주체 |

| 부스 교환 | 대상 A/B의 현재 배치 확인 → 목표 부스 선택 → 전체 검증 → 원자적 교환 → 변경 안내 초안 | operation_id, 기존/신규 assignment, actor, 사유 |
| 첨부 교체 | 허용 상태 확인 → 새 키 업로드 → 완료시 상태/기한 재확인 → 새 첨부 연결 → 이전 첨부 이력 보존 | attachment_id, storage_key, 신청 revision_no/version 증가 |

업무 변경은 현재시각 < projects.event_end_at이고 프로젝트가 COMPLETED가 아닐 때만 허용한다. 행사 당일에도 이 조건 안에서 참가확정·취소·부스 변경·긴급 안내를 처리한다. 마감 후에는 신규 업무를 만들지 않되 기존 AI/발송 작업 결과 기록, UNKNOWN 결과 확인, 감사로그 추가, 개인정보 보관·삭제 관리 작업은 권한을 검사해 허용한다.

## 10 발송 요청과 중단 복구 절차

<a id="table-29"></a>
**표 29**

| 상황 | 운영 절차 |
| --- | --- |
| 승인 후 대기 | READY를 유지한다. 발송 버튼을 누르기 전에는 외부 제공사 호출을 하지 않는다. |
| 발송 요청 | 대상 수·내용 확인 → send → QUEUED → worker 처리 → SENDING → 제공사 결과 확인 |
| 전송 전 대상 변경 | 취소·부스·이메일 변경과 함께 READY/QUEUED의 승인 및 대기열 정보를 무효화한다. worker와 같은 잠금 순서를 따른다. |
| 요청 응답 유실 | 화면에서 결과 확인을 제공한다. 새 키로 다시 실행하지 않고 기존 요청의 키·본문을 재사용한다. |
| 사진 여러 장 | 파일별 업로드·연결을 순서대로 처리하고 완료 개수를 표시한다. 실패/미완료가 남으면 제출을 막는다. |
| 요청 결과 만료 | EXPIRED이면 재실행하지 않고 현재 신청·발송 목록과 감사 이력을 확인한다. 확인되지 않으면 운영자 확인 대상으로 남긴다. |

요청 중복 방지 레코드와 업무 변경·이력·비동기 작업 생성은 같은 DB 트랜잭션으로 커밋한다. IN_PROGRESS는 미커밋 처리 중에만 존재하며 별도로 저장하지 않는다. 커밋 전 중단은 전체 롤백, 커밋 후 응답 유실은 같은 키와 본문으로 저장된 결과를 재조회한다. 외부 AI·메시지 호출은 커밋된 작업을 worker가 처리한다.
