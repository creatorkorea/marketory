# 인증 화면 및 요청 복구 설계

사용자 승인 범위: 다음 작업 1~3(Supabase 개발 연결, OTP·세션 UI, 요청 복구)의 진행 요청. 기존 v1.3/UX 계약을 확장하며 업무 역할이나 모집 정책은 변경하지 않는다.

## 화면과 구성
- `/login`: 크림 배경·상단 차양·Pretendard. 왼쪽 브랜드 소개, 오른쪽 최대 560px 이메일/인증번호 폼. 모바일은 한 열. 실제 이메일 전송 성공 후 인증번호 단계, 오류는 입력 곁에 유지. 60초 재전송 대기는 UI 기본 하한이며 provider 제한은 우선한다.
- `/account`: 현재 서버가 확인한 계정, 프로필 준비 상태, 로그아웃. 업무 신청/프로필 편집 기능은 아직 연결하지 않는다. 초기화 응답 유실은 이 화면에서 복구한다.
- Button/Input 재사용, 공통 Field·Notice·RequestStatus 추가. 중요한 오류는 지속 inline, 장식용 차양은 헤더 한 번만.

## 인증과 보안
브라우저 Supabase JS SDK가 이메일 OTP·세션 갱신·로그아웃을 담당한다. 이번 앱은 인증된 HTML을 SSR하지 않는 CSR 계정 화면이며 서버는 항상 Python API가 인증과 권한을 다시 검증한다. SSR cookie 세션을 병행하지 않는다.
SDK의 브라우저 localStorage 세션 저장을 명시적으로 사용한다(재접속·자동 갱신 목적). 토큰은 JS 접근 가능하므로 HTML 삽입/외부 스크립트를 추가하지 않으며 로그·URL·별도 앱 저장소에 복제하지 않는다. service role/DB 비밀은 브라우저로 전달하지 않는다. 이후 개인화 SSR 도입 시 별도 cookie 설계로 전환해야 한다.
Next `/api/backend/[...path]`는 허용 경로/메서드만 Python에 전달하고 Authorization/Idempotency-Key만 선별 전달한다. 응답은 no-store, upstream redirect 거절, timeout은 결과 불확실로 처리. 공개 페이지나 클라이언트 user metadata는 권한 근거가 아니다.
현재 목적지는 `/account`만 허용하여 외부 redirect를 차단한다. 로그아웃·다른 계정 로그인은 화면 결과를 즉시 지우고 진행 중 조회를 취소한다.

## 복구
`auth.bootstrap` 빈 본문과 actor별 UUID 키만 sessionStorage에 보존한다. 토큰·이메일·업무 본문은 복구 저장소에 남기지 않는다. 새로고침/재인증에도 기존 키 우선. 브라우저 저장이 막히면 실행 전 안내하며 임의 키로 재시도하지 않는다.
불확실 응답 뒤 2/4/8초 대기 → 조회 → UNRESOLVED일 때만 원래 키/본문 재시도. 3회 후 수동 확인. 401 재인증, 403/404 권한 안내, 409 충돌/운영자 확인, 410 만료는 자동 재실행 금지. 성공 뒤 `/me`로 최신 권한 재확인. Abort는 서버 취소를 의미하지 않는다.

## 검증·외부 전제
복구 core 단위 테스트(시간·키·HTTP·중단·actor 격리), proxy allowlist 테스트, 브라우저 OTP/복구/반응형/키보드 테스트. provider는 테스트에서만 네트워크 mock하며 운영 bypass는 추가하지 않는다.
2026-10-09 연결 계정 조회에 MARKETORY 프로젝트 없음. 사용자에게 project ID 또는 조직·리전을 요청했다. 생성 비용·조직 선택이 필요한 신규 프로젝트를 임의로 만들지 않는다. 실제 migration/OTP 수신은 외부 연결 후 증거로 별도 기록한다.
